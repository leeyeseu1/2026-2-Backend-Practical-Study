# 1주차 WIL

테스트로 시작하는 도메인 리팩터링 (2026.09.16)

## 시작하기 전에

정규 스터디를 아직 다 듣지 못한 상태로 참여해서, 솔직히 첫 주부터 모르는 단어가 많았다. @Setter가 뭔지도 몰라서 찾아보는 것부터 시작했다. 자바에서 필드를 private으로 막아두면 바깥에서 값을 못 바꾸니까 setStock() 같은 메서드를 만들어 통로를 열어주는데, 롬복의 @Setter는 그걸 모든 필드에 대해 자동으로 만들어주는 기능이었다. 이걸 알고 나니 이번 주 강의가 무슨 얘기를 하는 건지 겨우 따라갈 수 있었다.

## @Setter를 열어두면 생기는 일

@Setter를 붙이면 setStock()이 만들어지고, 그건 프로젝트 어디에서든 호출할 수 있다는 뜻이다.

```java
product.setStock(-5);   // 컴파일도 되고 에러도 안 남. 그냥 재고가 -5가 된다
```

재고를 줄이는 메서드에 "1개 이상만", "재고보다 많이는 안 됨" 같은 검증을 아무리 잘 써놔도, 검증을 건너뛰고 값을 바꿔버리는 옆길이 항상 열려 있는 셈이다. 에러가 안 나니까 나중에야 발견된다는 게 더 무섭다고 느꼈다.

또 setStock(7)이라는 코드만 봐서는 왜 7이 됐는지 알 수가 없다. 주문이 들어와서 줄어든 건지 재입고를 한 건지 구분이 안 된다. decreaseStock(3)처럼 이름을 붙이면 무슨 일이 일어난 건지 코드만 읽어도 알 수 있다.

## Tell, Don't Ask

강의에서 본 원래 코드는 Service가 상품에게 상태를 물어보고 직접 판단하고 있었다.

```java
if (quantity < 1) throw ...;
if (product.getStatus() != ON_SALE) throw ...;
if (product.getStock() < quantity) throw ...;
product.setStock(product.getStock() - quantity);
if (product.getStock() == 0) product.setStatus(SOLD_OUT);
```

재고가 얼마인지 아는 건 Product인데 판단은 Service가 하고 있다. 그래서 이 검증들을 Product 안으로 옮기고 @Setter를 지운다. 그러면 Service는 한 줄이 된다.

```java
product.decreaseStock(quantity);
```

물어보지(ask) 말고 시켜라(tell). 데이터를 가진 객체에게 일을 맡기라는 뜻이다. 이렇게 하면 재고를 줄이는 방법이 decreaseStock() 하나뿐이라 우회로가 없어지고, 규칙이 바뀌어도 고칠 곳이 한 군데다.

그럼 @Getter도 지워야 하나 싶었는데, 그건 아니었다. 화면에 상품 이름이랑 가격을 보여주려면 값을 꺼내와야 하고 읽기만 하는 건 값을 망가뜨리지 않는다. 다만 꺼내온 값이 바깥의 if문 조건으로 들어가고 있으면, 그건 Product가 해야 할 판단을 밖에서 대신 하고 있다는 신호라고 이해했다.

## 테스트 코드

구조를 바꿨으면 동작이 그대로인지 확인해야 한다. 예전 같으면 서버 띄워서 Postman으로 하나씩 쏴봤을 텐데, 코드 고칠 때마다 그걸 반복하는 건 무리다. 테스트 코드가 그 확인을 자동으로 해준다는 게 이번 주에 제일 와닿았다. 테스트를 '다 만들고 나서 하는 검사'로만 생각했는데, 리팩터링을 겁내지 않게 해주는 안전망에 가깝다는 쪽이 더 이해가 잘 됐다.

```java
@Test
void 재고가_0이_되면_품절_상태가_된다() {
    // given: 재고 3개짜리 상품이 있고
    Product product = new Product("사과", 1000, 3);

    // when: 3개를 구매하면
    product.decreaseStock(3);

    // then: 재고는 0이고 상태는 품절이어야 한다
    assertThat(product.getStock()).isEqualTo(0);
    assertThat(product.getStatus()).isEqualTo(SOLD_OUT);
}
```

@Test가 붙은 걸 찾아서 실행해주는 게 JUnit, assertThat() 같은 읽기 좋은 검증 문법을 주는 게 AssertJ다. 둘 다 spring-boot-starter-test에 이미 들어 있다. given(이런 상황에서) - when(이렇게 한다면) - then(이렇게 되어야 한다)이 테스트를 쓰는 기본 틀이다.

테스트에도 종류가 있었다. 단위 테스트는 위처럼 객체 하나만 놓고 작은 동작을 확인하는 것이고, 통합 테스트는 상품이 DB에 제대로 저장되는지처럼 여러 구성 요소가 맞물려 도는지를 테스트용 DB를 붙여서 확인한다. 그 외에 E2E, 스모크, 부하, 경계값 테스트 같은 말도 나왔다.

TDD, Mock, Stub, Fake도 언급됐는데 이건 아직 이름만 아는 수준이다. TDD는 테스트를 먼저 쓰고 그걸 통과시키는 코드를 나중에 쓰는 방식이고, Mock/Stub/Fake는 진짜 객체 대신 세워두는 가짜들이라고 들었다. 결제 테스트를 하는데 진짜 카드사에 요청을 보낼 순 없으니 성공했다고 대답만 하는 가짜를 끼워넣는 식이라는데, 셋이 정확히 어떻게 다른지는 아직 모르겠다.

## 회고

지금 정규 스터디를 같이 듣고 있는 중이라 선수 내용이 부족한 상태다. 그래서 강의 중에 당연하게 지나가는 단어들이 나한테는 다 찾아봐야 하는 것들이고, 솔직히 어렵다. 그래도 이번 주 내용은 Spring이나 JPA의 깊은 부분이라기보다 자바 객체를 어떻게 설계하느냐에 가까운 얘기여서, 모르는 단어만 하나씩 메꾸면 따라갈 수 있겠다는 생각이 들었다. 정규 스터디 진도를 부지런히 따라잡으면서 공부해보려고 한다.
